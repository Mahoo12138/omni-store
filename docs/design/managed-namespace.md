# `.omnistore/` 托管命名空间与 404 契约

> 修订：2026-09-29 / R2。2.0 目标规范；未标为基线的内容不代表已实现。

状态：2.0 目标安全契约。该文件描述文件服务边界，不是一个可以由外部请求打开的“内部模式”。

## 1. 布局与归属

```text
Storage Source/
├── blog-assets/                 # 普通文件；可配置为静态资源发布目录
├── documents/                   # 普通文件
└── .omnistore/                  # 源根目录唯一托管根
    ├── image-bed/
    └── transfer/
        ├── send/
        └── collect/
```

SQLite、密钥、配置、缓存和恢复日志仍在实例系统数据目录，不因命名简化而搬到每个 Source。临时上传需同目录原子安装的约束继续保留；原 `.omnistore-upload-*`、`.omnistore-copy-*` 保留规则不取消。

系统实际只在 Source 根创建 `.omnistore/`。用户输入的任意路径段都不得为 `.omnistore`，用于防止嵌套目录的移动、导入和跨协议歧义。不能用 `strings.HasPrefix(name, ".omnistore")` 误伤 `.omnistore.txt` 等普通名字；原临时前缀单独判断。

## 2. 通用访问规则

完成协议要求的认证后，通用资源层命中保留目录段时，不报告“这个隐藏目录存在但没权限”。按普通不存在资源返回：

| 入口 | 直接访问 `.omnistore` 或后代 | 父目录枚举 |
| --- | --- | --- |
| 文件 REST 列表/详情/下载/raw/preview | 404，普通 FILE_NOT_FOUND 语义 | 无该条目 |
| 公开盘/raw、静态资源路由 | 真实 HTTP 404，no-store | 公开盘隐藏；静态资源无列表接口 |
| WebDAV GET/HEAD/PROPFIND | 404；HEAD 无体 | PROPFIND 不包含该成员 |
| S3 GET | 404 / NoSuchKey | ListObjects 不包含该 key |
| S3 HEAD | 404，无响应体 | 同上 |
| Search/Recent/Favorite/Share 输入 | 不授予或暴露该资源 | 结果中剔除 |
| `/.omnistore/...` 直接站点 URL | 在 SPA fallback 前返回 404 | 不适用 |

未认证协议仍按原认证流程处理，不能为保证“总是 404”而绕过签名或暴露鉴权侧信道。S3 DELETE、批量结果等操作保持协议自己的非泄漏语义，但绝不能触碰真实内部文件；404 契约重点是直接读取和浏览。有效 JSON/Form 中明确指向保留目标的普通写入请求按不存在资源拒绝；格式非法的原始请求仍可返回 400。

HTTP 返回 404 隐藏被禁止资源符合标准允许的做法；具体依据见 [参考资料](../REFERENCES.md)。

## 3. 不能只做 HTTP 前缀过滤

路径可能来自路由、query、WebDAV Destination、S3 key、multipart relative_path 或 JSON body。所有入口都必须调用统一的路径解析与资源服务检查。

处理顺序：严格解析请求 → 对输入做一次协议规定的解码 → 拒绝非法段/越界 → 规范化相对路径 → 检查保留段 → 安全解析到 Source 内。不得先 clean 掉危险 `..` 再判断；不得后续重复 percent-decode。

编码的 `.`、`/`、反斜杠、双重编码与代理重写都纳入测试。合法字面 `%`、`_`、空格、Unicode 文件名保留：编码两次的字面百分号不应再次被解释为路径分隔符。若某种编码有歧义，可拒绝，不得降级到不安全路径。

从已经打开且验证的路径/文件句柄进行读取，检查和使用之间不允许通过软链接替换逃逸。不能只检查请求字符串而跟随文件系统软链接。宿主机直接写磁盘者属于部署信任边界，但服务不能把普通请求升级为该权限。

## 4. 间接操作也受边界约束

目录递归 Share、ZIP、复制、移动、删除、回收站、S3 listing 与后台扫描都必须识别该边界。

只读列表/打包可以跳过内部命名空间；必须只输出普通可授权内容。可能移动或删除托管根的递归写操作则整体拒绝，不能“跳过一部分后报告全部成功”。Source 根本身不允许普通移动/删除。

Search 即使读到旧 FTS 行，也必须再次执行资源范围过滤。仅前端隐藏目录、仅给前缀加 exclude，或依赖随机 ID 难猜，都不满足规则。

## 5. 专用服务访问

图床以 image_id 查询自己记录，Transfer 以任务/提交 ID 和业务授权查询自己的记录。专用接口根据受信任 Source ID 与已登记内部路径构造访问上下文；不能把用户 relative_path 直接接到 `.omnistore/` 后面。

内部写入仍检查源状态、路径安全、配额、操作锁、WebDAV 相关并发约束、日志及事务。可以重构共用底层 primitive；不能在公共 DTO 增加 `allow_internal=true`，也不能把普通用户伪装成超级管理员。

## 6. 所有权与异常数据

存在 `.omnistore/` 名称不能证明它属于 OmniStore。首次托管初始化应记录源 ID、实例持久标识及随机 ownership nonce，创建受限权限标识文件并在数据库保存对应登记。单独一个可由用户伪造的 marker 仍不能证明所有权，实际维护需核对登记与业务记录。

发现未知同名目录：不接管、不清空、不递归 chmod/chown、不让 GC 删除；图床/Transfer 的绑定进入 blocked，管理员处理。公开盘与静态资源不需要创建托管根；它们仍隐藏该目录并展示诊断，但不必仅因旁边有未知目录就停止发布其他普通文件。

## 7. 台账与物理空间

源物理统计包括 `.omnistore/` 下的所有普通文件、临时文件和未知同名内容；不要跳过整个目录后声称有空余配额。

普通 Reconcile 不把托管文件导入普通台账，也不能把已经登记的托管图床行当作“本轮未扫描到”删除。图床台账 scope 与普通文件分开过滤；Transfer 使用独立台账。异常清理由所属服务操作，quota 计量不是删除授权。

## 8. 代理与验收

推荐反向代理只转发给 OmniStore，不能用 Nginx alias、静态托管插件或 CDN 源站直接映射整个 Source，从而绕过保留目录、停用、类型和路径检查。单独资源域名只反代 `/assets/` 等公开业务路由，不路由后台 API。

真实 HTTP 测试须覆盖现存与不存在内部路径、超级管理员、普通用户、匿名、签名 S3、WebDAV、查询参数、Destination、文件夹上传、Range 和 SPA fallback。目录页显示“404”但网络状态 200 不算通过。
