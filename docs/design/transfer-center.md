# 文件中转设计

> 修订：2026-10-05。本文描述当前中转任务、身份与公开访问边界；接口见 [API](../API.md)，用户流程见 [功能说明](../features/transfer-center.md)。

## 1. 领域与页面职责

`internal/transfers` 管理发件包、收集任务、提交批次、载荷台账、访问会话与清理。中转任务具有独立的存储和生命周期，不作为 Share 子类型。

`/transfer` 和 `/app/transfer` 共用 `TransferWorkspace`，以发送、收集、收发记录三个 outline Tabs 分组。公开页使用统一深色 masthead/hero 与下方 workbench；创建、设置、记录管理不采用嵌套弹窗。

查询参数保存页面状态：`view=send|collect|history`，详情增加 `record=send|collect&id={id}`。刷新详情直接请求所有者 GET-by-ID 接口，即使任务已超出最近 200 条列表窗口，也能够按权限读取。身份切换后按 `owner_key` 隔离记录与界面状态。

`/pickup/{publicKey}` 和 `/collect/{publicKey}` 是独立公开任务流程。它们直接打开任务，不解析门户 URL 输入、不枚举短码。公开任务组件按 publicKey 重新挂载；同一收集任务的重新验证保留已选文件、姓名和留言，切换任务则丢弃上一个任务的访问会话和草稿。

## 2. 所有者身份

中转所有者可以是登录用户或独立访客。`GET/POST /api/v1/transfer-identity` 返回当前中转身份、稳定的界面隔离键、该身份的 CSRF、截止时间与限制。优先使用有效登录用户会话；访客仅由独立、不可猜测的 Cookie 识别。

访客 Cookie 为 HttpOnly、SameSite=Lax，Path 为 `/api/v1`。身份和 CSRF 由服务端验证，不使用邮箱、姓名、publicKey 或界面缓存授权。访客身份不能被普通登录中间件识别为用户，不能进入普通来源管理或应用管理。

`v2.0.0` 使用独立 `transfer_guest_identities` 表保存访客 Token 的摘要与期限，任务所有者由 user ID 或 guest ID 二选一；迁移不重建已有任务表，短码要求与载荷关系保持原语义。访客 CSRF 从 Cookie 凭据作独立单向派生，Cookie 原值不返回给脚本。登录身份响应的 `limits` 为 null，访客响应才包含访客限额；两种身份都返回当前身份截止时间。

中转所有者 API 允许当前用户或访客读取、上传、定稿、撤销发送任务，创建/关闭收集任务，以及读取自己的提交批次。写请求必须匹配当前身份的 CSRF。读取其他所有者的 ID 统一返回不存在。

从网盘复制和将提交保存到普通文件仍要求真实登录，并对每个来源/目标子树执行 Policy。登录不会自动把原访客任务迁移到账号；当前也不提供跨设备或邮箱恢复。

访客身份期限取配置的 Web 会话期限与 7 天的较小值。访客新任务不超过身份截止时间，网页限定 1 天；访客活跃任务数上限为 20，活跃载荷和单文件均不高于 1 GiB，单文件还受上传配置限制，写入继续检查站点中转配额与存储源物理配额。身份建立与访客任务创建按客户端 IP 限流。

## 3. 内部载荷布局

当前逻辑相对路径为：

```text
<task-source>/
└── .omnistore/transfer/
    ├── send/<publicKey>/<file-relative-path>
    └── collect/<publicKey>/<submission-id>/<file-relative-path>
```

载荷通过托管命名空间访问，普通文件接口不能列出或写入内部路径。任务固定保存创建时的源 ID；站点 capability 重绑只影响新任务。公开 API 不接受真实根路径或任意内部路径。

## 4. 发送快照与定稿

发送流程为 `创建 draft → 上传/复制文件 → finalize → active`。每个文件通过托管写入与相对路径校验，写完后增加任务文件台账。草稿只允许其所有者写入；至少有一个文件才能定稿，active 后拒绝继续上传。

从网盘选择文件时复制独立载荷，检查逐路径读取权限与中转/源配额。原文件后续移动、删除或修改，不影响中转副本；过期清理只处理副本。

前端保留已成功上传项，失败项独立重试。存在未完成或失败上传时不自动定稿；定稿失败保留草稿供明确重试。记录页面可以继续完成已有草稿，而不是重新创建并重传成功文件。

## 5. 收集批次

公开提交为一次 multipart 请求中的 N 个文件：`name`、`note`、重复的 `relative_path` 与重复的 `file` 按索引配对。不提供公开提交列表、读取、删除或猜测 submission ID 后续传的入口。

服务端检查当前任务和访问会话、必填信息、相对路径、扩展名、单文件大小、任务累计总量以及中转/源配额。逐个写入载荷后，在事务中登记本批文件、数量、大小与任务汇总。遇到写入或约束失败时回滚本批记录并删除本批载荷，不把部分文件作为成功提交呈现。

写入前持久化 `submission-batch` 日志，记录任务源、collection ID、submission ID 与批次目录。空 submission 行只是分配的占位，不作为已提交凭证，也不显示在收件箱。恢复时验证文件清单与批次数量/大小一致后才判定提交；未提交则删除该批次载荷与空行。启动恢复同时处理占位已创建、日志尚未写入的中断窗口，正常服务期间不会执行这一无年龄门槛的启动扫尾。

前端文件与文件夹选择累加，保留相对层级；重复路径需先移除或重命名。客户端预检用于快速反馈，服务端约束仍是权威。上传、网络或重新验证错误保留本批草稿；成功回执仅描述当前提交，不包含他人的提交。

## 6. 短码、密码与公开访问会话

publicKey 是高熵任务链接。短码只用于已知 publicKey 的访问验证，不定位或搜索任务。需要短码时生成随机码并保存 HMAC 摘要；密码保存密码摘要，列表与详情不返回明文凭据。

`require_code` 与 `has_password` 独立。网页创建默认关闭短码，显式传 `require_code=false`；API 省略字段保留 `true`。`v2.0.0` 建表时 `require_code` 默认 `1`，省略字段的写入不会意外取消短码保护。

没有短码和密码要求时，公开页仍调用 unlock 获取该任务的 Bearer 会话；其余情况只显示任务实际要求的输入。unlock 依据 IP + 任务限流。访问会话最多 12 小时，且不超过任务截止时间；仅授权一个发件包或收集任务，不转化为所有者或普通登录身份。

访问会话失效与任务不存在目前都可能返回 `FILE_NOT_FOUND`。公开页先重新获取任务摘要：任务有效则重新验证，任务关闭/过期/撤销则显示终止状态；网络失败可重试。访问 Token 仅通过 Authorization 头携带，不加入 URL、Cookie 或持久化历史。

## 7. 下载与次数

公开取件界面提供文件列表、单文件下载和 ZIP。现有 raw API 与文件下载共用处理器；本轮未增加在线预览系统。

文件下载/raw 与 ZIP 都在服务端通过条件 UPDATE 原子预占一次下载名额，不会因并发超过 `max_downloads`。预占发生在打开文件和发送响应之前，之后的文件错误或流中断不返还次数。当前未实现按 Range/重试复用次数的 download session；不得把它描述为现有保证。

ZIP 直接流式写入响应，不生成临时压缩包。公开读取使用当前任务的访问会话和任务原始源，响应使用 no-store。

## 8. 关闭、过期与清理

发送状态为 `draft → active → expired/revoked`；收集状态为 `active → closed/expired/revoked`。关闭收集立即停止新提交，已有提交仍由所有者读取。撤销发送停止领取并清理载荷，状态记录保留。

清理只处理由数据库任务/提交记录证明归属的过期任务、撤销载荷和遗留草稿/空提交。详细托管根安全规则以 [命名空间契约](managed-namespace.md) 为准。不得扫描普通静态发布目录或根据未知目录名推断归属。

站点服务关闭、解绑或换源与任务撤销不同：前者控制新任务创建，后者控制指定任务的公开访问。历史任务继续使用原始源，实际可用性仍受该源与载荷状态影响。

收集 `closed` 表示停止收件，不能作为删除载荷的条件。关闭后的已有提交仍占用站点与访客字节配额、保留源引用保护；运维的进行中任务数仍仅统计 active，载荷用量包含 closed。到达原 `expires_at` 后，GC 将 closed 转为 expired 并回收载荷；无期限任务持续保留。保存到普通目录的副本不随该清理删除。

## 9. 保存到普通文件

登录收集者把批次复制到普通存储源时执行目标写权限、相对路径、保留名称、锁与配额检查；目标同名冲突显式失败，不自动覆盖。副本进入普通文件台账，原提交保留到自身生命周期结束。

保存到静态发布目录只是创建一个普通副本，其公开性由目标的静态 HTTP 配置决定。中转期限不应用到图床和长期博客资源，清理不删除这些普通副本。

## 10. 崩溃恢复边界

发送上传采用 `send-file` 日志，写入前记录最终路径和同目录的精确临时路径。临时写入、文件 fsync、原子发布与业务事务仍分阶段进行；恢复按文件台账决定保留已提交文件或清理未提交载荷。日志新增可选字段，不修改 SQLite schema 或历史 migration；旧发送日志仍可读取，但没有记录的旧临时路径不能凭名称猜测归属。

恢复首先验证日志格式、文件名与操作 ID、任务与源对应关系、载荷路径以及托管根登记。无法证明归属时保留日志和文件并阻止启动；清理失败保留日志以便重试。日志持久化和移除同步目录，清理未完成时不抹去恢复依据。

运行时 GC 不再扫描名称匹配的孤儿临时文件或数字提交目录。未知旧残留保留供管理员核查；新上传由精确日志在启动时收敛。有残留上传日志的任务/空批次保留归属台账，避免 GC 先删除任务导致恢复无法核验；发送写入、定稿与过期草稿删除共享任务级锁，并在清理锁内重查状态。

收集没有独立 finalize：一个公开 multipart 请求就是一个批次事务。保存到普通文件按每个文件提交，进程中断后允许保留完整的先前文件，但不能留下损坏文件或改变原提交；重试仍受同名冲突规则约束。

托管回滚复用普通删除 primitive 时，通用路径恢复同样必须校验托管根。已标记 database-ready 的删除只清日志，不再重放删除，以免破坏后来写入的同名内容；未完成删除/移动仍占用相关路径，托管上传拒绝复用，直至恢复完成。
